# Запуск в Docker

Добавьте недостающие переменные из `.env.example` в существующий `.env`.
Не заменяйте сохранённый ключ API примером. Для PostgreSQL задайте пароль,
а для webhook — секрет, совпадающий с настройкой GitHub.

```powershell
docker compose up --build -d
docker compose logs -f
docker compose down
```

Проверка: `http://localhost:8080/health`.
Webhook: `http://localhost:8080/webhook`.
Для GitHub при локальной разработке направьте HTTPS-туннель на порт 8080.

nginx передаёт запросы на `server:8000`. Flask запускается через Gunicorn.
PostgreSQL доступен контейнерам как `postgres:5432`; его порт наружу не открыт.
Параметры подключения переданы серверу и агенту через переменные `PGHOST`,
`PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`.

Токен аккаунта бота храните в корневом `.env` как `GITHUB_TOKEN=...`.
Compose передаёт его только контейнеру агента. `.env` исключён из Git и контекста
сборки; токен не требуется добавлять в Dockerfile или URL репозитория.
GitHubClient использует токен для API, RepositoryLoader — для приватного git fetch.
Временная Git-конфигурация авторизации передаётся через окружение subprocess,
не записывается в кеш. После изменения `.env` пересоздайте агент:
`docker compose up --build -d agent` (одного restart недостаточно).

Для fine-grained PAT скачиванию кода нужно Contents: Read, логам — Actions: Read;
созданию PR — Pull requests: Write. Публикации веток понадобится Contents: Write.
Приглашённому collaborator могут потребоваться PAT classic с repo scope или GitHub App.
GITHUB_TOKEN и GITHUB_WEBHOOK_SECRET — разные секреты.

Пока сервер только проверяет и логирует webhook. Агент забирает задания из tasks
и загружает точный коммит через RepositoryLoader, затем получает логи нужной
попытки CI через GitHubClient и сохраняет в ci.log. Уже существующий ci.log
не перезаписывается. Запись заданий сервером и сохранение итогового статуса
ещё не подключены. Метод создания draft PR реализован, но воркер его не вызывает.
Схема таблицы и её применение описаны в `db/README.md`.

Данные репозиториев хранятся в volume `agent_repos`, подключённом в `/app/repos`.
Для каждого репозитория: `repos/owner/name/cache.git` и
`repos/owner/name/workspaces/task-ID/`. Рядом можно добавлять другие данные проекта.

Вывод агента сохраняется отдельно от кода в `repos/owner/name/logs/task-ID/`.
Каждая попытка выполнения создаёт новый файл
`attempt-N_<время-UTC>_<уникальный-id>.log`: повторы не перезаписывают старые журналы.
В нём находятся начало задания, подготовка кода и CI-логов, задача модели,
текстовые ответы модели, аргументы и результаты инструментов, ошибки с traceback.
Результаты инструментов записываются без прежнего обрезания до 200 символов
(собственные ограничения размера вывода инструментов сохраняются).
Тот же журнал выводится в stdout: `docker compose logs -f agent`.
Значения настроенных токенов и паролей маскируются при форматировании журнала.
Файлы сохраняются в том же volume `agent_repos`; автоматическая очистка старых
журналов пока не настроена. Ошибки опроса БД вне задания выводятся в консоль.
Скачанные логи GitHub Actions по-прежнему лежат отдельно в рабочем `ci.log`.

Прежние volumes `agent_git_cache` и `agent_workspaces` автоматически не переносятся
и не удаляются. С новой структурой кеш заполняется заново.
Загрузчик скачивает нужный коммит без полной истории и создаёт отдельный worktree.
Повторная загрузка того же SHA использует кеш. Существующая непустая рабочая папка
не перезаписывается; очистка worktree и политика хранения кеша добавятся отдельно.
Пока поддерживается последовательная работа одного воркера, без загрузки LFS
и подмодулей. Для приватных репозиториев требуется GITHUB_TOKEN;
недоступный SHA (включая коммит из другого репозитория PR) приводит к ошибке.

Данные PostgreSQL и рабочие папки агента находятся в отдельных named volumes.
Обычный `docker compose down` их сохраняет. Флаг `-v` удаляет эти данные.
После создания базы смена `POSTGRES_PASSWORD` в `.env` не меняет пароль
существующего пользователя PostgreSQL.

Оба Dockerfile устанавливают Python-зависимости на этапе builder и копируют
готовое окружение в runtime. Файл `.env` не включается в образы.
Агент содержит Git; зависимости и изоляция для тестируемых проектов добавятся позже.

Текущий nginx принимает HTTP. Для постоянного размещения на сервере потребуется
настроить HTTPS с сертификатом. При внешнем HTTPS-туннеле Flask видит внутреннюю
схему HTTP; сейчас обработчик не строит внешние ссылки и редиректы.
